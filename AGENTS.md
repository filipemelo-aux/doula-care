Atendimentos com valor positivo criam imediatamente uma receita vinculada em Contas a Receber; pagamentos totais ou parciais são registrados nessa receita, sem etapa de previsão ou faturamento — para manter o serviço e seu recebimento no mesmo fluxo.
Fallback de parcelas sem transaction_id só é permitido para receitas automáticas de contratos — para não misturar parcelas antigas de acompanhamentos com pagamentos de atendimentos da mesma cliente.- iOS/Android in-app purchases use @revenuecat/purchases-capacitor (official, Capacitor 8 + Swift Package Manager); never the deprecated @capgo/capacitor-purchases.
- Never return a Capacitor plugin proxy directly from an async function or promise; wrap it (e.g. `{ plugin }`) — the proxy answers `.then()` and breaks `await` on iOS.
- Client plan display always resolves clients.plan_setting_id -> plan_settings (name + features expanded as consultations, sequence = index+1) via src/lib/clientPlan.ts; legacy clients.plan enum is never shown — avoids stale Básico/Intermediário/Completo labels.
- Each service_record links to its agenda appointment via service_records.appointment_id (created together, edited/completed/deleted together); payment actions live only in Contas a Receber — avoids atendimentos missing from the Agenda.
- Native subscriptions (iOS and Android) go through AppStoreSubscriptionService + RevenueCat with keys read from system_config; the Subscription page enables purchase on web, iOS and Android — one purchase path for both stores.
- Super Admin announcements use the protected send_in_app_announcement RPC and per-user in_app_announcements rows, polled by the global notification provider with persistent acknowledgement; keep this delivery separate from push to avoid external notifications.
- Notification device targeting is stored on announcements and matched against the current access platform; push filters actual subscriptions before deduplication using the shared server matcher, so other platforms remain registered.
- Client list access limits resolve pregnancy IDs through src/lib/clientPlanAccess.ts before display filtering, with deterministic DPP ordering — prevents search or tabs from changing which pregnancy is accessible.
- Organization sheet PDFs are generated by src/services/orgSheetPdf.ts using existing authorized reads, with one organization per A4 page and no client records — keeps bulk printing simple and avoids exporting unrelated sensitive data.
- Labor start and contraction deletion use src/lib/laborActions.ts with changed-row readback, and shared action controls across alerts — prevents silent RLS no-ops and separates labor start from birth registration.
- Birth action availability uses src/lib/birthRegistration.ts independently of labor tracking — keeps all alert surfaces consistent for births without labor or contractions.
- Booking conflicts use src/lib/bookingAvailability.ts in São Paulo time; approval refreshes reservations excluding only the request being approved, so it cannot conflict with itself or bypass another booking.
- Admin banner destinations use src/lib/notificationDestination.ts; appointment requests open Agenda rather than the general notification center.
- Agenda owns the selected day and availability-dialog state; its shared sticky action bar exposes both creation flows in either view without coupling creation access to filters.
